# BuildScope — концептуальная модель данных (этап 2, черновик 0.1)

**Статус:** архитектурный проект для проверки, **не утверждённая SQL-схема и не реализация**. Основание: [FUNCTIONAL_SPEC.md](./FUNCTIONAL_SPEC.md) и [PRODUCT_STATE.md](./PRODUCT_STATE.md). **Один новый BuildScope**, без разделения на версии/продукты и без опоры на старое приложение. Физическое хранение пока не выбрано.

## 1. Принцип
Один реестр **физических строительных сущностей** и связанных с ними работ. 3D, дерево, таблица, документы и аналитика — проекции одних и тех же идентификаторов. Строительная сущность может не иметь геометрии. Проектные версии и фактические записи хранятся отдельно; прошлые подтверждённые сведения не изменяются задним числом.

## 2. Сущности и связи (концептуально)

| Домен | Сущности | Основные связи |
|---|---|---|
| Организация проекта | Project, ConstructionSite, Zone, Structure, ElementType, PhysicalElement, ElementGroup | Site → Project; Zone/Structure → Site/родитель; PhysicalElement → ElementType и местоположение; Group ↔ Element |
| Геометрия и чертежи | GeometryRepresentation, Drawing, DrawingRevision, DrawingSheet, SourceReference, ImportBatch, ImportProposal, DesignChange | Geometry → PhysicalElement (необязательно); источник → конкретная редакция/лист; предложение изменения → затронутые элементы |
| План и исполнение | WorkType, WorkScope, WorkOrder, WorkOrderLine, Shift, WorkReport, ReportLine, QuantityRecord, QuantityAllocation, Verification | WorkOrderLine → WorkScope/Shift/исполнитель; ReportLine → WorkOrderLine или отдельно добавленная работа; QuantityRecord → стадия, единица, источник |
| Участники | Organization, ContractorRelation, Person, Crew, CrewMembership, ShiftAssignment, TimesheetEntry, SignatureEvidence | Crew/Person → Organization; назначения → Shift/WorkOrder; подписи → человека, момент начала/конца, документ |
| Техника в работах | EquipmentReference, EquipmentAssignment, Waybill, EquipmentWorkSegment | назначение/путевой лист → смена, объект, работа, участки; **нет самостоятельных сущностей ремонта, ТО и допусков** |
| Материалы и имущество | MaterialDefinition, MaterialRequirement, SupplyRequest, SupplyRequestLine, Delivery, MaterialBatch, StorageLocation, StockMovement, ConsumptionAllocation, InventoryItem, Handover, Reconciliation | требования → элементы/работы; партия → поставка; движение → источник/получатель; расход → работа/группа/элемент |
| Документы | Document, DocumentRevision, Attachment, ApprovalRoute, ApprovalStep, ApprovalDecision | редакции → объект/работа/наряд/элемент; решения → точная редакция и уполномоченного |
| Контроль и коммуникации | Task, Issue, Assignment, Comment, GroupConversation, Message, Event, NotificationRule, Notification | ссылки на объекты/работы/документы, аудит авторов и действий |
| История | Actor, AuditEvent, EvidenceLink, DataOrigin | кто/когда/откуда/что изменил; origin может быть бумага, Excel, ручной ввод, подрядчик, CAD/PDF |

**Примечание:** имена сущностей — предлагаемые технические названия. Связи многие-ко-многим, ключи и таблицы уточняются после проверки сценариев. Нельзя трактовать таблицу как разрешение создавать отдельный экран для каждой сущности.

## 3. Инварианты (проверяемые правила)
1. **PhysicalElement.id** не зависит от марки, которая может повторяться; тип и экземпляр различаются.
2. **GeometryRepresentation** необязательна. Отсутствие mesh не удаляет элемент, работу или источник.
3. **WorkOrderLine** и **ReportLine** сохраняют связь с конкретной сменой; ночная смена может закончиться на следующий день.
4. План, заявление подрядчика, проверка координатора и формальная приёмка — **разные состояния/записи**. Переходы требуют полномочий и истории; доказательство (фото/видео) само по себе не повышает стадию.
5. **QuantityAllocation** распределяет исходный групповой объём, а не создаёт второй расход/факт. Сумма распределения не превышает доступный объём в той же единице и стадии; остаток видим.
6. **MaterialBatch/StockMovement/ConsumptionAllocation** обеспечивают прослеживаемость без двойного списания; нераспределённый расход не превращается автоматически в складской остаток.
7. Документ, согласование, расчёт и работа ссылаются на **действовавшую редакцию** источника; новая редакция не переписывает принятый исторический факт.
8. Для количеств сохраняются единица, основание, метод, уровень достоверности и статус «неизвестно» отдельно от числового нуля.
9. Подписи начала и окончания смены — самостоятельные свидетельства; их проверка не доказывает часы автоматически.
10. **Actor/Origin** различают введённое координатором сообщение подрядчика, прямое цифровое сообщение подрядчика и подтверждённую координатором проверку. Система не создаёт несуществующее цифровое подтверждение подрядчика.
11. Доступ определяется **действием + областью** (организация, объект, участок, работа); серверная проверка обязательна при многопользовательском доступе.
12. Нет финансовых таблиц, расчётов с подрядчиками и отдельного эксплуатационного контура техники.

## 4. Жизненные циклы — пока без фиксации точных статусов

**Наряд:** черновик → согласование/выдача → исполнение → полученный отчёт → построчная проверка → дальнейшая приёмка (если требуется). Отмена, блокировка редакцией чертежа и возврат на доработку — отдельные переходы, а не удаление истории.

**Изменение чертежа:** загрузка редакции → извлечение/сопоставление → предложения изменений → проверка последствий → подтверждение уполномоченным → обновление действующего проекта. Не менять исторические факты.

**Материал:** заявка → поставка/партия → перемещения/передачи → расход/возврат/выяснение расхождений. Одна операция движения имеет уникальный источник и не учитывается дважды.

**Подключение новых участников:** подрядчики получают права к существующим данным; сохраняются авторство и происхождение фактов, отдельная миграция между версиями продукта не нужна.

## 5. Архитектурные риски и вопросы для проверки
- **Единый продукт:** самостоятельный ввод координатором и будущий доступ подрядчиков — роли и каналы работы одной системы.
- Единицы измерения и конверсии: нельзя автоматически суммировать м³, м², штуки и тонны.
- Исторические редакции типовых элементов и индивидуальные исключения требуют временной модели, а не обновления одной строки без истории.
- Подтверждённые и непроверенные факты должны различаться в API, экспортах, аналитике и 3D.
- Складская инвентаризация и имущество — строительные рабочие сведения, не универсальная ERP.
- Реальные Excel/PDF/путевые листы нужно сверить с полями модели до физической схемы.
- Не использовать старый Project JSON v1/v2 и архитектуру старого приложения как проектные ограничения.

## 6. Следующий архитектурный результат
1. ER-диаграмма с кардинальностями, ключами, областями доступа.
2. Словарь полей и статусы основных сущностей, включая отсутствие данных.
3. Проверка сценариев S1–S10 из спецификации на отсутствие дублирования.
4. После этого — выбор физического хранилища, синхронизации и границ API.
