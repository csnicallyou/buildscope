# BuildScope — проверка полноты спецификации и границ (этап 1)

**Дата:** 19.11.2026. **Статус:** ревизия доступных в GitHub источников выполнена; сверка отсутствующих оригиналов Excel/PDF остаётся внешней зависимостью, а не поводом задерживать архитектурное проектирование.

## Проверенные источники
- [PRODUCT_STATE.md](./PRODUCT_STATE.md): 66 разделов второго уровня; исходный журнал решений и поздних уточнений.
- [FUNCTIONAL_SPEC.md](./FUNCTIONAL_SPEC.md): консолидация 0.1–0.2, дополнения по Personal и Platform.
- [REQUIREMENTS_TRACEABILITY.md](./REQUIREMENTS_TRACEABILITY.md): тематическая трассировка всех 66 разделов.
- Ранние документы о Personal/Platform **исключены из нормативной базы** по прямому решению пользователя.
- Документы старого viewer и его архитектура **не рассматриваются как основа нового продукта**.

## Снятые противоречия
1. **Один новый BuildScope** без отдельных версий Personal/Platform. Все каналы ввода и роли работают в одной предметной модели.
2. **Техника** участвует в нарядах, табелях, путевых листах и заявках; самостоятельный эксплуатационный ERP с ТО/ремонтом/допусками **исключён** поздним прямым уточнением. Старые предложения о ремонте инвентаря не становятся обязательными.
3. **Снабжение, склад, имущество, инвентаризация** сохраняются, но бухгалтерия, цены, платежи, зарплаты — нет.
4. **Старое приложение не рассматриваем**: не переносим код, интерфейс, архитектуру или его форматы как требования.
5. **Фото** как вложения и фото бумажных нарядов утверждены; обязательность конкретных фото для каждого вида работ пока не утверждена.
6. **Текущий бумажный процесс** и **будущие кабинеты подрядчиков** сосуществуют в общей предметной модели; цифровое подтверждение нельзя выдумывать в системе.
7. **Состояния количеств** не сводятся к одному «факту»: план/заявлено/проверено/принято. Подтверждение переноса OCR ≠ проверка выполнения ≠ официальная приёмка.

## Восстановленные детали, критичные для приёмки
- Смены через полночь, отсутствие данных отдельно от нуля, поимённый табель и сводные трудовые единицы, два независимых свидетельства подписей.
- Контроль выхода по фото листа после начала смены; «нет сообщения» не означает «не вышли».
- Форма наряда: лицевая сторона с планом/фактом/дополнительными работами; оборот с работниками, временем и подписями; ручной ввод и OCR с проверкой.
- Подрядчики могут предлагать планы; координатор проверяет, корректирует и выдаёт наряд. Цифровая выдача/подтверждение получения доступна при подключении подрядчиков.
- Очередь проверки по станциям/подрядчикам/сменам; построчная частичная проверка; заявленное не перезаписывается; спорная часть и причина остаются.
- Техника сторонних организаций: госномер, путевой лист, часы по участкам, неопределённость простоев/пересечений.
- Снабжение: ручная заявка без обязательной связи с 3D, частичные поставки, календарь; материалы и индивидуальное имущество; подтверждение передачи.
- Объект без геометрии и работа без 3D равноправны; пространственная локализация факта не выдумывается.
- Групповые объёмы и материалы распределяются по экземплярам без двойного счёта; неизвестный остаток видим.
- Изменение чертежа создаёт предложения с оценкой последствий и не переписывает подтверждённую историю.
- Автоматическая сменная сводка для копирования в групповой чат; не путать её с обязательной автоматической отправкой.

## Внешние зависимости, не блокирующие концептуальную архитектуру
- Оригинал `Наряд общий МЦД Ярославское(1).xlsx` и его шесть листов; в журнале есть перечень колонок, но это **не повторная проверка файла**.
- Оригинал `10-25-М-КЖ1.5 (7)(2).pdf`; инженерная реконструкция документирована, но оригинал в GitHub отсутствует.
- Реальный путевой лист и подписи для точной печатной формы, правил часов и верификации.
- Юридические маршруты ЭП/ЭДО и полномочия формальной приёмки.
- Точные правила обязательных фото, сроки уведомлений, матрица прав и конкретная навигация.

## Решение о переходе
