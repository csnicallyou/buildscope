# BuildScope — архитектура хранения и доступа (проект этапа 2)

**Статус:** рекомендуемое техническое решение, 19.11.2026. До реализации и выбора хостинга — не финальная инфраструктурная спецификация. Один новый BuildScope, без изучения или наследования старого приложения.

## 1. Рекомендуемый базовый стек

- **PostgreSQL** как транзакционная реляционная база: сущности объектов, смен, нарядов, фактов, складских проводок, версий, ролей и аудита. `NUMERIC` для количеств; `timestamptz` для событий плюс IANA timezone объекта.
- **Объектное хранилище S3-compatible** для оригиналов Excel/PDF/DWG/IFC, фото, вложений, 3D-ассетов. База хранит ID, контрольную сумму, MIME, размер, права и ссылки на неизменяемые версии, но не двоичные файлы в строках.
- **Backend API с единой авторизацией и транзакциями**. Клиент не пишет напрямую в таблицы. Операции нарядов, отчётов, материалов и согласований выполняются как атомарные команды.
- **Асинхронные задания** для OCR, импорта чертежей, извлечения геометрии, построения 3D, предпросмотров и тяжёлых отчётов. Результат импорта — предложение, не автоматическое изменение утверждённого факта.
- **Web UI** для координатора, подрядчиков и руководителей с различными правами. Мобильная адаптация — обязательное требование к UX; нативные приложения и офлайн-режим — отдельные решения после проверки сценариев.

Стек — предпочтение для будущего техплана, **не разрешение начинать код**.

## 2. Границы модулей одного приложения

| Модуль | Владеет | Публикует/читает |
|---|---|---|
| Реестр объектов | Project, Site, SpatialNode, ElementType, PhysicalElement, WorkScope | идентификаторы для всех модулей |
| Проектные данные | DrawingRevision, SourceAnchor, DesignSnapshot, GeometryRepresentation | действующие версии и предложения изменений |
| Планирование | Shift, WorkTarget, WorkOrder, WorkOrderLine | планы смен и общий целевой объём |
| Исполнение | WorkReport, ReportLine, ReportedWork, WorkActual, WorkActualRevision, WorkActualAllocation | подтверждённый координатором факт, накопительный прогресс |
| Люди и техника | Organization, Crew, ShiftParticipation, TimesheetEntry, SignatureEvidence, EquipmentUse, Waybill | сменные сведения без отдельной ERP |
| Снабжение и склад | SupplyRequest, Delivery, Batch, StockMovement, MaterialConsumption | единый журнал остатков |
| Документы и согласования | DocumentRevision, ApprovalDecision, Attachment | неизменяемые версии и основания |
| Задачи и взаимодействие | Task, GroupChat, Message, CalendarEvent | контекстные ссылки и события |
| Доступ и история | Actor, RoleGrant, OriginRecord, AuditEvent | централизованные проверки и журнал |

**Не создавать отдельную базу на каждый модуль:** это один продукт с едиными идентификаторами, транзакциями и реестром прав. Модульные границы логические; начальная реализация может быть модульным монолитом.

## 3. Физические правила данных

1. Первичные ключи — UUID; внешние ключи и ограничения ссылочной целостности в PostgreSQL. Удаление утверждённых исторических записей запрещено: отмена/архивирование через состояние и аудит.
2. `WorkTarget` — отдельный общий план; `WorkOrderLine` — назначение на смену; `WorkActual` + immutable `WorkActualRevision` — факт смены. **Накопительный итог вычисляется**, не редактируется отдельно.
3. Текущая редакция факта определяется указателем `current_revision_id` и блокировкой версии. Создание редакции и смена указателя происходят в одной транзакции; устаревшее конкурентное обновление отклоняется.
4. Склад: `StockOperation` (уникальный `operation_key`) и `StockPosting` (партия, место, signed_quantity). Остаток = сумма проводок. Расход/передача/возврат — атомарные операции; `MaterialConsumption` только указывает назначение расходной операции, не списывает второй раз.
5. `WorkActualAllocation` относится к конкретной редакции факта. Ограничение суммы распределений проверяется транзакционно, не простым `CHECK` одной строки.
6. Единицы измерения имеют измерение/масштаб/точность. Преобразования разрешены внутри одной размерности; масса→объём требует явно подтверждённой плотности и основания.
7. Источники данных, вложения и редакции документов неизменяемы. Повторный импорт распознаётся по `source_id` + идентификатору строки + ревизии; подозрительные совпадения требуют сопоставления человеком.
8. `unknown`, `known_zero` и `not_applicable` — разные состояния. Неизвестные записи не превращать в нули при агрегировании.
9. Текущая проекция прогресса может кэшироваться для скорости, но должна восстанавливаться из первичных фактов и редакций; кэш не является источником истины.
10. Для связей с документами/чатами/задачами использовать типизированные ссылки или отдельные link-таблицы с проверкой существования и доступа; не полагаться на бесконтрольные строки `entity_type/entity_id`.

## 4. Матрица прав (начальное предложение)

| Действие | Координатор | Подрядчик | Руководитель | Администратор |
|---|---|---|---|---|
| Читать назначенные объекты | в своей области | только разрешённые | в своей области | согласно административным полномочиям |
| Создавать/выдавать наряды | да | нет | по отдельному праву | не автоматически |
| Вносить бумажный отчёт | да, с origin=paper | нет | по отдельному праву | не автоматически |
| Подавать собственный цифровой отчёт | по праву | да, по своему наряду | по праву | не автоматически |
| Устанавливать рабочий факт | да | нет | по отдельному праву | не автоматически |
| Исправлять факт | да, с причиной и аудитом | нет | по отдельному праву | не автоматически |
| Утверждать документы | при выданном праве | при выданном праве | при выданном праве | не автоматически |
| Складские операции | при выданном праве | при выданном праве | при выданном праве | не автоматически |
| Выдавать права | нет | нет | по отдельному праву | да, в пределах своей области |

**Все «да» ограничены областью**: project/site/zone/work order/organization. Подрядчик не читает чужие отчёты или внутренние групповые чаты без отдельного доступа. Администратор не получает автоматического права менять производственный факт без явно выданного полномочия.

## 5. Потоки и границы API

- `issueWorkOrder`: проверить права и редакцию наряда → создать неизменяемый снимок выдачи → записать AuditEvent → инициировать генерацию Excel/PDF.
- `submitReport`: принять файл/цифровую форму → связать с origin и сменой → создать строки и предложения сопоставления → **не устанавливать автоматически подтверждённый факт**.
- `recordActual`: проверить роль, область, работу, единицу, ревизию → создать WorkActualRevision → переключить current_revision_id → аудит → пересчитать проекцию прогресса.
- `postStockOperation`: проверить права, идемпотентность, доступный остаток и единицы → записать проводки одной транзакцией → аудит.
- `importDrawingRevision`: сохранить исходник и хэш → асинхронно извлечь данные → подготовить diff → пользователь проверяет предложения → новая версия проекта без переписывания истории.
- `grantAccess`: проверить право делегирования и границы области → создать/отозвать RoleGrant → аудит.

Это **контракты на уровне команд**, не окончательные URL, JSON-схемы или микросервисы.

## 6. Риски и условия перед кодом

- Проверить реальные бланки нарядов, Excel, путевых листов и PDF: без оригиналов невозможно утвердить точное сопоставление колонок.
- Утвердить экранные сценарии этапов 3–4, прежде чем выбирать окончательные формы API.
- Проверить нормативные и организационные требования к подписям/официальной приёмке; обычный рабочий факт координатора не должен блокироваться юридическим процессом.
- Решить стратегию резервных копий, восстановления, хранения оригиналов, лимиты файлов, секреты, HTTPS, журнал доступа, тестовые окружения и бюджет при этапе 5.
- Отдельно определить, нужен ли полноценный офлайн-режим на стройплощадке; не обещать синхронизацию без проектирования конфликтов.

**Вывод:** предложена конкретная, проверяемая архитектура хранения, модульные границы, права и транзакционные потоки. Достаточно для перехода к информационной архитектуре и UX; физические миграции и код пока не создаются.
