# Общая работа BuildScope 0.11

Это режим одного сервера Node.js 24 с локальной SQLite, а не синхронизация через GPT. Тот же интерфейс можно запускать отдельно через Vite без сервера: тогда остаётся прежний браузерный архив. Production-пакет собирается с `VITE_WORKSPACE_API=required` и при отказе API показывает ошибку, не подменяя общие данные локальным архивом.

## Работа бригады

- Руководитель создаёт пользователей, составляет и выдаёт наряды, исправляет план с причиной, принимает сдачу и возвращает запись на исправление. Бригадир записывает факт, выполнение, фактическое время и фото в своей бригаде. Наблюдатель читает. Это разграничение нарядов и фото; модели пока общие для всех вошедших пользователей.
- «Наряды по дням» хранит дату начала, дневную/ночную смену и бригаду. Выдача сохраняет снимок плана, потребности и привязок. Факт появляется при сдаче, не при составлении. Сданную запись может открыть для правки только руководитель с причиной; прежние снимки и автор остаются в истории.
- «Ход работ» показывает потребность модели, сданный факт, остаток и назначенный план отдельно по операции и области элементов. Неизвестные значения и разные единицы/основания не складываются. Пересекающиеся области с разными потребностями требуют уточнения, а не вычисления по габаритам.
- При новой выдаче сервер проверяет известный остаток и уже назначенный план, включая другие смены и бригады. Ручная работа без известной потребности не получает выдуманного ограничения. Импорт старых нарядов сохраняет исторические записи даже при конфликтующих старых назначениях; дальнейшие назначения требуют уточнения.
- «Перенести незавершённое» готовит черновик на другую дату/смену/бригаду. План продолжения — прежний план минус известный факт; при неизвестном факте план пустой. Новый наряд выдаётся после проверки пользователем. Отметка выполнения исключает строку из переноса.
- Цвета в модели отражают назначенные работы, а не полную физическую готовность конструкции. Они не меняют геометрию, Project JSON, расчёт материалов или GLB.
- Фото/замечания открываются из свойств объекта/части и из строки сдачи. Крупные фотографии уменьшаются в браузере до 1600 px, перекодируются в JPEG; EXIF не переносится. Сервер принимает JPEG/PNG/WebP до 5 МБ. Доступ к изображениям также требует входа и подходящей бригады.
- Черновик руководителя сохраняется с задержкой 800 мс. Локальная страховочная копия помогает восстановиться после сбоя. Два устройства не перетирают изменения молча: версии наряда и черновика проверяются сервером. При конфликте нужно загрузить актуальную версию явно. Список обновляется при возвращении в окно и каждые 30 секунд.
- Прежние браузерные наряды переносятся вручную: «Команда и доступ → Перенести прежние наряды из этого браузера». Открывать нужно прежний адрес и браузер. Источник не удаляется; совпадающие ID повторно не добавляются. Самостоятельно неизвестный браузерный архив сервер получить не может.

## Развёртывание

```powershell
npm.cmd ci
npm.cmd run typecheck
npm.cmd run lint
npm.cmd test
npm.cmd run build
npm.cmd run e2e
npm.cmd run build:deploy
npm.cmd run e2e:workspace
```

`.deploy/release/web` и `.deploy/release/server/index.mjs` — готовый самодостаточный пакет. Сборка на рабочем ПК; на малой ВМ не нужны npm, Docker или сборка frontend. Node.js 24 нужен также для тестов, использующих `node:sqlite`.

Сервер слушает только `127.0.0.1:8780`. Переменные: `BUILDSCOPE_DATA` (закрытый постоянный каталог), `BUILDSCOPE_WEB` (собранный frontend), `PUBLIC_ORIGIN` (точный HTTPS origin, включая порт), `TRUST_PROXY=1` только за доверенным локальным Caddy. При разработке можно указать `DEV_ORIGIN=http://127.0.0.1:5173`. Production получает Secure/HttpOnly/SameSite=Strict cookie; изменение данных требует подходящего Origin. Пароли — scrypt с индивидуальной солью, токены сессий в БД хешируются, сеанс действует 12 часов. Вход ограничивает число неудачных попыток. API и все файлы модели защищены сеансом; публична только самостоятельная страница входа и health/session.

Первый руководитель создаётся однократно командой `node index.mjs bootstrap`: JSON с username/name/password поступает через stdin, а не аргументы командной строки. Пароли не писать в репозиторий/логи. Пользователей затем создаёт руководитель в интерфейсе. SQLite schema v1 отделена от формата Project v1/v2 и браузерного архива v1.

`deploy/prepare.sh`, `deploy/provision.mjs`, `deploy/activate.sh` описывают первоначальную установку именно на существующую ВМ пользователя: Node 24.19.0 из официального дистрибутива с проверкой SHA256, отдельный системный пользователь, systemd, постоянная БД, Caddy. Скрипты привязаны к текущему адресу и проверенной конфигурации одного сайта. Не запускать повторно bootstrap на рабочей базе. `scripts/provision-remote.mjs` передаёт новые пароли по SSH stdin, хранит их только в исключённом `.deploy/access.json` с закрытыми правами. Исходный SSH-ключ никогда не копируется на сервер.

## Резервные копии и восстановление

SQLite работает в WAL, foreign_keys включены; изменения наряда и соответствующее событие пишутся одной транзакцией. Резервные копии создаются SQLite backup API, а не копированием открытого WAL-файла. Автоматический интервал сервера — 24 часа; при `EXTERNAL_BACKUPS=1` вместо него используется systemd timer. В установленной конфигурации это 03:15 UTC ежедневно с небольшим случайным сдвигом и выполнением пропущенного запуска. Последние 30 снимков лежат в `/var/lib/buildscope/backups`. Руководитель может создать и скачать снимок из интерфейса. Копии включают пользователей, хеши паролей и сеансов, наряды, черновики, историю и изображения: они конфиденциальны, их нельзя класть в публичный web-каталог или Git.

Восстановление выполняется администратором ОС: остановить `buildscope`, сохранить текущий каталог данных отдельно, проверить выбранный snapshot через `PRAGMA integrity_check`, заменить `workspace.sqlite` проверенным снимком, убрать только принадлежащие прежней БД `workspace.sqlite-wal`/`workspace.sqlite-shm` после остановки всех процессов, восстановить владельца buildscope и права 0600, запустить сервис и проверить вход/наряды. Откат текущих данных требует отдельного решения пользователя, поскольку удалит изменения после снимка.

Копия на той же ВМ не защищает от потери ВМ. После первоначального развёртывания один согласованный snapshot дополнительно скачивается на рабочий ПК в исключённый `.deploy/backups`. Постоянное внешнее резервирование ещё не настроено. Исходная конфигурация Caddy и прежняя статическая версия сохранены на ВМ в `/var/backups/buildscope-before-<release>`; вернуть статический сайт можно копированием сохранённого Caddyfile и reload Caddy, серверные данные при этом не удаляются.

## Дополнение 0.14

Рабочие записи подрядчиков, техники, путевых листов, заявок и предложений сохраняются в той же защищённой общей БД. Независимая проверка объёмов использует PUT `/api/orders/:id/review`, дополнительные работы — POST `/api/orders/:id/additional`. Обычный save не даёт подменить проверенные поля. Видео выдаётся защищённо с MIME/Range после проверки доступа. Подробности, совместимость и границы: [SHIFT_OPERATIONS.md](SHIFT_OPERATIONS.md). Schema2 сохраняется; старый сервер 0.13 не понимает новые виды записей, поэтому не является совместимым откатом после их появления.

## Ограничения

Один процесс/одна ВМ и небольшой коллектив; для нескольких серверов потребуется другая архитектура БД/файлов. Привязки моделей сейчас относятся к двум реконструированным сборкам и пользовательским локальным моделям; полного каталога всех объектов нет. Наряды сохраняют снимки строк, не загружают пользовательский Project на сервер. У всех вошедших пользователей доступ к поставляемым моделям; ограничение моделей по объектам ещё не реализовано. Фото не служат подтверждением скрытых работ автоматически. Счётчик готовности и остатка основан только на зарегистрированных операциях, не на полном ППР или исполнительной документации.
